## 代码为什么能成为策略

Code as Policies（CaP）不满足于让 LLM 排列“抓取、放置”技能名称，而让它生成 Python 程序。程序可使用条件、循环、函数、NumPy 和几何库，把语言要求转成可计算的空间关系，再调用已有感知与控制 API。新增任务不一定需要训练一条新的神经策略；也可能只是重新组织已有能力。（§III）

## 从指令到一次机械臂操作

以“把积木排成托盘左边的一条线”为教学例子：模型收到任务、可用 API 及少量示例，生成查询积木和托盘位置的代码；数值计算确定线的方向、间距与目标点；程序依次调用抓取放置原语。感知返回坐标，机器人控制器完成轨迹跟踪。语言模型不负责每个伺服周期，也不天然拥有准确的三维感知。

核心技术是层级代码生成：上层程序若使用尚未定义的辅助函数，系统再提示模型补出函数实现。这样可以把对象解析、几何运算和动作编排拆开。程序还可以在 `while` 循环里查询新观测，所以 **CaP 不等于开环执行**。应区分“程序内读取反馈”与“运行中的 LLM 看反馈后改写程序”，两者的时间尺度和能力不同。

## 已证能力及其前提

作者使用预训练代码模型，未为这些任务微调 LLM，但下游检测器、抓取放置原语和控制接口已经具备能力。论文展示 UR5e 桌面操作、绘图及移动操作等真实平台；受控机器人量化比较主要在仿真任务族，真实开放任务以演示为主。（§IV）

标题页的 HumanEval 39.8% 是通用代码题指标，不能当成机器人操作成功率。实际操作更受感知误差、底层原语能力和 API 约定限制。生成程序通过语法或受限执行检查，也不等于完成了物理安全证明。（§V）

## 为什么它仍是今天的起点

VoxPoser 将代码输出收束到空间价值图，ReKep 收束到关键点约束；AGP 等新工作把运行时观察、编程和修改程序进一步交给通用 coding agent。这里的“后续”表示共同问题与方法联系，不声称所有论文直接继承同一实现。

当前 RPent 已有固定工具和 VLA 接口。可研究的问题是：固定动作工具之上，预先生成一段带反馈的程序，和每个工具结束后让 Agent 再决策，分别适合哪些任务？必须固定感知、动作权限与总预算。仅仅把工具调用包装成 Python，不自动构成新的算法贡献。
