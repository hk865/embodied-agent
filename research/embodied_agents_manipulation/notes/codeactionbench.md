## 先固定比赛规则，再比较 Agent

CodeActionBench 的价值是明确输入与评分边界。被测系统要根据多视角 RGB、标定几何工具和机器人反馈，自己估计三维关系、构造目标位姿、编写或调用动作；任务判分由隐藏 verifier 在终止后完成，不把判分结果送给 Agent。（§3）

## “杯子挂上架子”如何评价

Agent 可以取图、选图像点、用校准几何算三维估计，再构造抓取/放置姿态。几何工具负责计算，但不替模型决定对应点，也不保证它对平面或几何关系的假设正确。运动工具执行给定 TCP 位姿和夹爪命令，规划失败或持续停滞时返回证据。Agent 说 `done` 只记录其完成判断；最后物理场景是否满足任务条件由另一条不可见评分链决定。

这区分了三种成功：工具调用合法、动作实际执行、任务目标达到。即使机器人到达了指定位置，物体仍可能滑落或落错地方。任务级误判完成因此成为可独立统计的失败类型。

## 具体评测范围

平台基于 SAPIEN/RoboTwin 2.0 的 ALOHA-AgileX，25 项操作任务，关闭域随机化，每任务固定一个场景 seed。九种 Agent 配置各做三次，共 675 次。21 项按最终状态评分，四项按过程中是否发生指定事件评分。（§3.1、§3.4–3.5）

最强配置为 55/75 次成功，即 73.3%；22/25 项至少成功一次，即 88% 的任务覆盖率。**88% 不是单次成功率**，也不是不同场景泛化率。同一模型搭不同 harness 的结果不同，比较跨 harness 配置时评价的是整套系统，不能全归因模型能力。（§4、图 3）

## 对我们最有价值的部分

本地应同样把环境原生真值留在评分链，把可见观测、工具返回和 Agent 完成声明记录清楚。若为了诊断把 simulator 物体位姿开放给 Agent，应另标 oracle 条件；否则很难知道改善来自规划能力还是额外真值。

这篇是评测论文，当前定向阅读不能代替完整 API 审计；也未核验到独立官方代码入口。它的固定场景设计适合控制变量，却不能直接回答大范围随机布局与真实世界泛化。
