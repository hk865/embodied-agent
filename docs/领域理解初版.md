# 具身 Agent：领域主线、系统边界与低资源研究路线

> 本文是具身 Agent 模块的总入口，综合课程要求、VLA、世界模型、感知、规划控制等目录中的知识，以及前期讨论形成的工程约束。重点不是设计一个“什么都做的大模型”，而是回答三个问题：为什么冻结 VLA 之外还需要 Agent/Harness；传统方法、世界模型与 VLA 如何分工；在单张 16 GB 显卡、无私有数据的条件下，怎样形成可复现、可证伪的课题。

## 0. 一句话结论

具身 Agent 不应进入高频伺服环，也不应替代 VLA、SLAM、规划器或控制器。它更适合作为 VLA 的外部运行时和控制平面：维护结构化任务状态，按事件选择类型化技能，监督有限时域动作，记录失败并触发恢复。VLA 作为局部视觉—语言—动作策略；传统规划器为可解析运动产生可行 reference，运动控制与独立安全层负责跟踪、约束和急停；世界模型只在确有收益时预测动作后果；SLAM只在移动与跨区域任务需要持久空间状态时加入。

在当前资源下，推荐主线是：

> 冻结 VLA 常驻 GPU + 少量解析原语 + CPU 规则 Verifier + 结构化任务/失败记忆 + 事件触发 Agent。

这是一项**待实验检验的系统假设**，不是已被领域证明的唯一答案。尤其不能预设“VLA 失败只因为上下文短”“LLM Agent 必然优于 FSM”或“传统方法终将被世界模型取代”。

### 0.1 主张与证据状态

| 主张 | 当前证据状态 | 本课题如何处理 |
|---|---|---|
| VLA 对外产生有控制语义的单步动作或 action chunk，而不是把视觉 latent 直接交给机器人 | 模型论文和代码已支持；具体维度依 checkpoint 与本体而变 | 作为接口事实 |
| π0.5 报告了 10–15 分钟的真实长程能力 | 原论文的长演示/能力描述达到 10–15 分钟；受控量化任务中许多 episode 约 2–5 分钟 | 分开表述演示尺度与量化评测尺度，不外推到本地 checkpoint |
| Harness 能提高冻结 VLA 在扰动任务上的成功率 | Harness VLA 预印本在多个仿真 benchmark 上支持 | 作为复现动机 |
| “VLA 上下文短”是长程失败的主要原因 | 仅部分支持；误差累积、目标错绑、遮挡、开环 chunk 和失败未发现也会导致失败 | 做 horizon scaling 与记忆消融 |
| 外部 LLM/VLM 是实现记忆的必要条件 | 未证实；结构化状态、FSM 或数据库本身就能记忆 | 比较 LLM Agent 与固定 FSM |
| 学习式 Verifier 比规则更好 | 未证实 | 规则先行，学习模型作为可选增量 |
| 完整 WM 或语义 SLAM 是桌面 Harness 的必要组件 | 不支持 | 不进入 MVP |
| Harness 的仿真收益能转化为真实机器人实时收益 | 尚无充分证据 | 只报告仿真结论，并单独测 wall-clock 与过期动作 |

### 0.2 当前课题定位

课程要求是把感知、导航、操作和交互封装成模块化工具，并实现 plan → execute → monitor 的多步任务闭环。LangChain/LangGraph 是实现这种编排的工程底座，不是研究贡献本身。

应把**课程系统验收**与**研究归因**分开：前者可以在一个小型服务机器人仿真演示中展示 perception、navigate、manipulate、interact 四类工具；后者聚焦冻结 VLA 的操作 Harness，在 LIBERO/LIBERO-Pro 上比较 Agent、Verifier 和记忆。LIBERO 没有移动导航，不能用其结果宣称已经验证完整服务机器人或 SLAM。实现上可用 LangChain StructuredTool 定义能力接口，用 LangGraph 维护状态图和事件转移。

更合适的研究问题是：

> 在不训练新 VLA、不部署第二个本地大模型的条件下，带有 typed event 监督和结构化失败记忆的最小 Harness，能否提高冻结 VLA 在多阶段扰动任务中的恢复率，并减少无效动作、重复失败和推理等待？若讨论“长程收益”，再用预注册 horizon bins 单独检验。

## 1. 概念边界：VLA 不等于 Agent

具身系统中的几个模块回答不同问题：

| 模块 | 回答的问题 | 典型输出 | 推荐运行方式 |
|---|---|---|---|
| 感知 | 当前看到了什么 | 对象、掩码、深度、位姿、置信度 | 持续服务或按需查询 |
| 状态估计 / SLAM | 机器人状态是什么；移动时地图是什么 | 关节/末端/基座位姿、地图、belief、协方差 | 本体状态估计持续运行；SLAM仅在移动/跨区任务持续运行 |
| Agent | 当前该做什么，调用哪个能力 | 子目标、工具调用、恢复决策 | 低频、事件触发 |
| 传统规划器 | 怎样在约束下到达目标状态 | 路径、轨迹或不可行结果 | 封装在导航/移动工具内部 |
| VLA | 当前局部场景中怎样行动 | 末端/关节动作或 action chunk | chunk 内通常近似开环，边界重观测形成闭环 |
| 世界模型 | 某动作之后可能发生什么 | 后继状态/观测，以及可选的风险、奖励或价值头 | 可选的预测/候选评价服务 |
| 控制与安全层 | 怎样稳定安全地执行 reference | 关节命令、力矩、限幅、停止 | 高频、不可被 Agent 绕过 |

可以用下面的关系避免概念混用：

$$
\begin{aligned}
\text{SLAM: } & p(x_t,m \mid o_{\le t},u_{<t}) && \text{结合观测与控制历史估计状态和地图}\\
\text{WM: } & p(z_{t+1} \mid z_t,a_t,c_t) && \text{预测动作后果}\\
\text{VLA: } & \pi(a_{t:t+H-1} \mid o_{\le t},l,s_t) && \text{产生局部动作}\\
\text{Planner: } & \arg\min_{\tau \in \mathcal F} J(\tau) && \text{求可行路径或轨迹}\\
\text{Agent: } & \operatorname{select}(u_k,g_k \mid b_k,M) && \text{选择工具与子目标}
\end{aligned}
$$

其中 $b_k$ 是结构化任务状态，$M$ 是外部记忆，$u_k$ 是一次类型化工具调用。Agent 的决策时刻 $k$ 通常远慢于控制时刻 $t$。

### 1.1 VLA 的 action chunk 是什么

对连续动作 VLA，一次调用通常产生：

$$
A_t=[a_t,a_{t+1},\ldots,a_{t+H-1}] \in \mathbb R^{H\times D}
$$

$H$、$D$、坐标系、绝对/增量表示都由 checkpoint 和机器人本体决定，不能把某个示例的 $H=50,D=7$ 当成 VLA 的统一定义。原始 OpenVLA 使用离散 action token 再反量化；π0/π0.5 的公开 openpi 推理路径支持 flow-matching 连续动作头。Agent 看到的 VLA_ACT 是人为封装的工具，而不是从 VLA latent 中自动析出的“原语”。

在本文的 Harness 语义中，VLA_ACT(max_chunks=N) 暂按“最多顺序调用 VLA N 次，每次产生一个 chunk”理解，不等于一次生成 N 个候选 chunk；正式实现前仍应以 RPent 对应版本的代码核验。它不是所有 VLA 服务的通用接口。当前硬件也不适合多候选采样再让大世界模型排序。

### 1.2 场景图属于 Harness 状态，不是通用 VLA 输入

对象表、目标绑定、已完成步骤和空间关系可以进入 Agent 的结构化状态。除非 checkpoint 明确用这种输入训练过，否则不应把 scene graph JSON 直接塞给 VLA。VLA 应继续接收训练分布内的图像、局部自然语言指令和本体状态；Agent 负责把全局目标改写成局部指令。

### 1.3 RAG 不等于机器人运行时记忆

RAG 适合检索操作手册、对象知识、技能说明和历史案例。当前位姿、对象状态、任务进度和最近失败属于强时效状态，必须进入结构化运行状态；把它们埋在向量库文档中会失去版本、坐标系和时间戳语义。

## 2. “长程”到底有多长

长程不能只用 prompt token 数或视频时长描述。建议把任务 horizon 记为：

$$
\mathcal H =
(N_{\text{subgoal}},N_{\text{primitive}},N_{\text{contact}},
T_{\text{episode}},N_{\text{recovery}})
$$

它至少包含子目标数、原语调用数、接触阶段数、物理持续时间和需要恢复的扰动数。对具身任务，更长的自然语言上下文并不能自动修复物理误差。


### 2.1 论文与常用评测中的尺度

| 任务尺度 | 典型例子 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 局部技能 | 抓取、插入、开门的一次或数次 chunk | 局部感知—动作能力 | 长程状态与恢复 |
| 多阶段桌面任务 | LIBERO；LIBERO-Pro 增加指令重定向和位置/对象扰动 | 短程组合、目标重绑定与 distribution shift | 单凭 Pro 不能证明 horizon scaling 或十分钟级实时性 |
| 长程家庭任务 | π0.5 的受控量化任务许多约 2–5 分钟；系统还报告 10–15 分钟的整屋清理能力 | 层级语义子任务 + 低层动作可支撑真实长程 | 不能把最长演示时长当成所有量化 trial 的统一长度，也不能外推到开源 checkpoint |
| 移动复合任务 | RoboCasa365 等 | 导航/预对位/接触阶段组合 | 已解决真实 SLAM、网络延迟与安全认证 |

π0.5 的关键不只是“上下文更长”：它在推理时先预测低频语义子任务，再基于该子任务生成低层 action chunk，并依赖大规模异构数据与专门后训练。原文称整屋清理可持续 10–15 分钟，而定量新家庭评测中的许多多阶段任务约 2–5 分钟；两种数字回答的不是同一个证据问题。因此，它证明层级化有价值，但不证明把任意 VLA 外接一个 LLM 就能复制其能力。

### 2.2 长程失败不只来自遗忘

长程成功率会受多类误差共同影响：

- 局部技能成功率小于 1，串联后误差累积；
- 目标对象被遮挡、交换或错误重绑定；
- chunk 在有限时域内近似开环，失败可能很晚才被发现；
- 缺少显式终止条件，成功后仍继续动作；
- 传统移动/预对位与 VLA 接触阶段接口不一致；
- 旧帧生成的动作在世界变化后过期；
- 恢复策略重复调用同一个已失败技能。

若每个阶段独立成功率为 $p$，理想化的 $n$ 阶段任务成功率约为 $p^n$。这只是直觉模型，但说明仅扩展 token context 不能消除物理误差累积。

所以，更准确的结论是：

> Agent/Harness 的价值假设，是把“任务状态、工具选择、完成判定和失败恢复”从局部 VLA 的动作上下文中解耦，而不是单纯给 VLA 接一段更长文字。

## 3. Harness VLA 提供了什么证据

清华大学为第一单位的 [Harness VLA](https://arxiv.org/abs/2607.08448) 将冻结 VLA 暴露为可重试的接触型 primitive，并与 grounding、staging、transport、navigation、release 等固定解析原语组合；[RPent](https://github.com/RLinf/RPent) 已公开代码。

### 3.1 关键结果

| 评测 | 冻结 VLA / 对照 | Harness 结果 | 应如何解释 |
|---|---:|---:|---|
| 标准 LIBERO | 同一冻结 checkpoint 95.3% | 96.0% | 原分布已饱和，Harness 增益很小 |
| LIBERO-Pro | 同一冻结 checkpoint 50.0% | Codex 72.1%，CC（Claude Code）82.4% | 扰动下重绑定、重预对位和工具组合有明显价值 |
| LIBERO-Pro Goal-S zero-shot / few-shot 对比 | 不检索目标设置的 Task Specific 与对应 Global Memory：31.0% | 使用 bootstrapped harness memory：87.0% | 整套 bootstrap memory 对空间过程组织帮助大，但不是单变量消融 |
| LIBERO-Pro Goal-T zero-shot / few-shot 对比 | 不检索上述两类 memory：79.0% | 使用 memory：87.0% | 在线 planner 已有较强语义重绑定；仍不能把差值只归因于 Task Specific Memory |
| RoboTwin C2R | LingBot-VLA 50.4% | 58.4% | 固定后端的随机化迁移有增益 |

论文还报告了 RoboCasa365 的复合任务增益，但不同工作使用的拆分与汇总口径并不完全一致，复现时应按任务、seed 和拆分报告原始分母，不能只复制 headline 数字。

### 3.2 这些结果尚未证明什么

Harness VLA 截至本文整理时仍是 2026 年 7 月的 arXiv 预印本，主要结果来自仿真。它没有替本课题回答：

- LLM Agent 是否比同样工具与重试逻辑的固定 FSM 更强；
- task-specific memory 学到的是可泛化策略，还是参考轨迹模板；
- 仿真暂停等待推理时的成功率能否转化为持续世界中的实时性能；
- 规则 Verifier、学习式 outcome predictor 与完整 WM 谁更划算；
- 真实机器人上的视觉跟踪、SLAM、碰撞与安全问题。

因此，合理目标是“复现并做严格归因”，而不是先宣称已经解决长程记忆。

还要注意，原 Harness 已经让 vla_act 以短 burst 执行动作 chunk，planner 提供 stop predicate / early-return 条件；Global Memory 也记录 empty-grasp 和 false-success 失败模式。任何“新增 Verifier”都必须先固定 RPent commit，核对原 stop 的信号、检查频率和返回语义。若只是重复原有 predicate，就只能算忠实复现；真正增量应明确落在确定性 typed failure、相同信号下的更低成本实现、chunk 内更高检查频率，或新的可部署观测上。

### 3.3 多模态 Agent 教程应怎样使用

[Multimodal Agent Tutorial](https://zsc.github.io/mm_agent_tutorial/) 更像一份工程推演和学习路径，不是带有数据集、对照实验和统计检验的论文。可借用其链路：

> Agent loop → structured memory → typed tool → simulator loop → trace → evaluation / distillation

但其中经验比例、延迟猜测和架构建议只能生成实验假设，不能当成领域事实。本文据此采用“教程给设计空间，论文给已有证据，本课题实验决定取舍”的证据分层。

## 4. 推荐的最小系统架构

~~~mermaid
flowchart TB
    U["用户长程目标"] --> TS["结构化 Task State<br/>目标绑定·进度·预算·最近失败"]
    MEM["Task / Episodic / Competence Memory"] <--> TS
    TS --> AG["事件触发 Agent / LangGraph"]
    AG --> SEL{"选择类型化原语"}
    SEL --> ANA["解析原语<br/>MOVE_TO·NAVIGATE·RELEASE"]
    SEL --> VLA["冻结 VLA_ACT<br/>局部语言 + 图像 + proprio"]
    ANA --> EXE["动作适配·控制·确定性安全限制"]
    VLA --> EXE
    EXE --> ENV["仿真 / 机器人"]
    ENV --> PER["持续感知 / 状态估计<br/>移动任务时包含 SLAM"]
    PER --> OBS["带时间戳的 RGB·proprio·belief·confidence"]
    OBS -->|"最新图像与本体状态"| VLA
    OBS -->|"任务 belief"| TS
    OBS -->|"位姿与约束状态"| ANA
    OBS --> VER["Verifier<br/>MVP: Chunk 边界<br/>增量: 低成本关键事件"]
    VER -->|"SUCCESS / CONTINUE"| TS
    VER -->|"EMPTY_GRASP / STALLED / UNSAFE"| TS
    TS -. "完成、失败、超时、目标变化时再调用" .-> AG
~~~

这里的 Agent/Harness 可以被视为 VLA 的**外部基础设施**，但更准确地说是运行时，而不是另一个基础模型。它至少包括：

1. 类型化工具注册与调用；
2. 结构化任务状态与记忆；
3. 带 obs_id 的观测/动作版本协议；
4. primitive 生命周期、超时、取消和错误码；
5. 安全中断与执行日志；
6. 可复现的评测 harness。

### 4.1 按物理阶段分工，而不是让两个控制器争夺同一动作

| 阶段 | MVP 首选 | 原因 |
|---|---|---|
| 自由空间移动、长距离搬运 | 解析规划—控制栈：IK/轨迹生成 + OSC/阻抗/PID；移动平台可用导航栈 | 状态和约束较明确，可解析方法高效稳定 |
| 预对位 / staging | 解析控制器 | 给 VLA 恢复到接近训练分布的局部初态 |
| 抓取、插入、开合等难解析接触 | 冻结 VLA action chunk | 学习策略更适合复杂视觉与接触先验 |
| VLA 执行期间 | 速度、工作空间、关节、碰撞等确定性限制 | 降低明显越界风险，不宣称形式化安全 |
| 搬运后释放、撤退 | 解析控制器 | 目标明确，避免浪费 VLA 调用 |

“VLA 负责接触、传统方法负责自由空间”是当前 checkpoint 与课题预算下的工程假设，不是普遍定律。若特定 VLA 在自由空间也明显更优，或任务特定 RL skill 在接触阶段更稳，应由对照实验改变分工。

MVP 不让监督/优化 MPC 在接触阶段与 VLA 同时写入同一动作命令。这样做容易造成目标冲突、观测与动作时间错位、chunk 不连续和分布偏移；但这不排斥下游 MPC 或其他控制器跟踪已经定义清楚的 reference。资源充足时，可研究“VLA 提议—WM 评价—优化器筛选”，但它不属于当前主线。

### 4.2 工具接口必须比自然语言更严格

建议工具至少声明：

| 字段 | 含义 |
|---|---|
| name / version | 技能名与版本 |
| arguments | 目标对象、局部指令、位姿或预算 |
| frame / timestamp / obs_id | 坐标系、捕获时间和观测版本 |
| preconditions | 可执行条件与置信度要求 |
| termination | 成功、继续、超时和失败条件 |
| interruptible | 能否在 chunk 内或边界中断 |
| budget | 最大步数、chunk 数、重试数与时间 |
| result | 标准状态、错误码、证据和新观测 |

一个结果可采用如下逻辑结构：

~~~yaml
status: SUCCESS | CONTINUE | EMPTY_GRASP | STALLED | UNSAFE | TIMEOUT
primitive_id: ...
obs_id: ...
chunk_id: ...
evidence:
  gripper_width: ...
  progress: ...
  target_track_confidence: ...
recoverable: true | false
~~~

其中 UNSAFE 是底层公共安全监控向上游传播的标准错误码，不是可由 Agent 绕过、也不是只在某个 Verifier 消融组中开启的能力。

持续运行的 SLAM、里程计、局部障碍检测、状态估计和安全监控不应由 Agent “临时启动”。Agent 只能查询它们的带时间戳结果。适合显式调用的是 navigate_to、move_to_staging_pose、vla_act、release、inspect_result 和 ask_user 等有完成语义的技能。

### 4.3 最小感知契约：目标和 staging 位姿不能凭空出现

删掉完整场景图和第二个大 VLM 后，仍必须说明 object binding、MOVE_TO 位姿和“目标是否随末端移动”的来源。推荐把感知条件分级报告：

| 等级 | 输入来源 | 用途与结论边界 |
|---|---|---|
| P0 Oracle | simulator object pose / contact；benchmark success predicate 默认只给 evaluator 和 episode termination | 可作为固定感知的因果主实验、系统联调或上界，但不代表可部署感知 |
| P1 Minimal | RGB-D 几何 + 轻量检测/分割 + 帧间跟踪 + proprioception | 部署性子实验；输出目标 ID、相对位姿、时间戳和置信度 |
| P2 Heavy | 大型 VLM/分割器或远程感知服务 | 仅在 P1 明确不足时加入，单独报告显存和延迟 |

Agent 只消费目标 ID、相对 staging pose、置信度与时间戳，不应自己从自然语言生成绝对坐标。若目标随末端运动，在 P1 中必须由视觉跟踪与本体状态联合估计；若直接读取 simulator truth，则该结果只能进入 P0/oracle 列。若把 benchmark success predicate 在线暴露给 Agent 或 Verifier，而不是只供 evaluator 终止 episode，必须另列 oracle-monitor 条件。

为控制工作量，M0–M3 的 Agent/记忆因果主实验可以先固定在 P0，并让所有 baseline 获得完全相同的 oracle 信息；P1 作为部署性子实验，只回答结论在非特权输入下保留多少。这样既不会把感知误差混入 Agent 对照，也不会把 P0 结果包装成可部署系统。

## 5. 用结构化状态实现记忆，而不是堆叠全部历史

外部记忆不要求 LLM/VLM 自己保存全部上下文。推荐分四层：

| 记忆 | 典型内容 | 更新频率 | 用途 |
|---|---|---:|---|
| Working / Task State | 当前目标、对象绑定、已完成步骤、当前 primitive、预算 | 每个事件 | 保持任务一致性 |
| Episodic Trace | 观测摘要、工具调用、结果、失败与恢复 | 每个 primitive/chunk | 复盘与失败检索 |
| Competence Memory | 某技能在对象/视角/初态下的成功统计与禁用条件 | 跨 episode | 选择技能和重试策略 |
| Spatial Memory | 地图、对象持久 ID、区域关系与不确定性 | 移动/跨区域任务 | 导航与目标再定位 |

桌面 LIBERO MVP 通常只需前三层中的最小字段，不需要完整场景图或语义 SLAM。推荐的 LangGraph 状态至少包括：

~~~yaml
goal: ...
current_subgoal: ...
object_bindings: ...
completed_subgoals: ...
active_primitive: ...
attempt_budget: ...
recent_failure: ...
recovery_history: ...
obs_id: ...
memory_refs: ...
~~~

### 5.1 记忆写入与评测隔离

为了区分“真正泛化”和“记住参考轨迹”，必须遵守：

- seed 0 或明确的 bootstrap split 只用于构造 task-specific memory；
- held-out seeds 评测时冻结记忆，禁止在线写回；
- 不保存并直接复用绝对位姿；保存相对关系、阶段结构、前置条件和失败模式；
- 位置、对象、视角或语言改变后仍有效，才算有迁移价值；
- 同 seed 记忆结果只能标为 replay/oracle，对外不能称泛化。

最小 competence memory 不需要神经网络。可用键：

$$
k=(\text{primitive},\text{object class},\text{relative staging bin},\text{observation/context bin})
$$

值中记录 success/failure 计数或 Beta-Bernoulli 后验，以及 failure-code 的类别直方图；若要按失败类型检索，可另建带 failure_code 的 episodic index。检索时返回相似条件下的成功率、禁用条件和替代 staging。若同一参数刚触发同类失败，当前 episode 内禁止原样重试，必须改变相对预对位、切换 primitive 或终止。held-out 评测仍允许更新 working state 和本 episode 的 recovery history，但禁止写回跨 episode 的持久记忆。

每次 Agent 决策只检索固定 top-k 条目，并设置独立 memory token 上限；按 primitive、failure type 和当前相对 context 过滤后再进入 prompt。外部存储可以增长，但在线上下文不能无界增长，否则只是把“短上下文”问题搬到 Harness。

## 6. WM、SLAM 与传统方法：方向不同，不是简单替代

### 6.1 本课题的四档预测实现范围

下表只表达本课题从简单到复杂的实现范围，不复用世界模型目录中的通用能力分级：

| 实现档位 | 输出 | 合适名称 | 当前是否做 |
|---|---|---|---|
| 规则判定 | 基于阈值的成功、空抓和停滞判断 | Rule Verifier | MVP |
| 结果分类 | $P(\text{result type}\mid state,primitive,parameters)$ | Outcome Predictor / Critic；不是完整 WM | 可选 |
| 状态转移 | 动作条件后继状态或 latent transition | Action-conditioned World Model | 未来方向 |
| 决策 rollout | 多步视频/状态预测、反事实候选评价 | Planning / Generative WM | 当前不做 |

只训练 success/failure 分类器时，最好称 Verifier 或 Outcome Predictor。显式预测动作条件后继状态时可称 action-conditioned WM；能否用于规划则是更高一层的决策证据，需要进一步证明反事实排序改善了闭环决策。正式能力等级沿用[世界模型领域总纲](reference/world-model/领域的理解.md)，不在本文另造同名分级。

第一版 Verifier 可利用部署时可获得的低成本信号：

- 夹爪宽度及其变化；
- 末端位姿变化和动作幅值；
- 目标相对深度或视觉跟踪结果；
- 目标是否随末端移动；
- 连续无进展步数；
- 可选的低分辨率目标 crop。

仿真 object pose、接触标签等 privileged state 可以生成监督标签或作为 oracle 上界，但不能混入“可部署输入”的主结果。

### 6.2 SLAM 解决当前状态，WM 预测未来

SLAM 估计位姿、地图、回环和漂移；WM 预测动作后果。语义地图或对象场景图仍首先属于空间状态，只有加入动作条件转移才是 WM。

因此：

- LIBERO 桌面任务：Agent 因果实验可固定 P0 oracle 并单独报告；部署性结论必须另做 P1。sim pose/contact truth 只能作 P0 输入、标签或上界；benchmark success predicate 默认只供 evaluator，在线暴露时另标 oracle-monitor；
- 移动厨房任务：可接入几何 SLAM、导航图和对象持久 ID；
- 真实跨房间任务：还需重识别、坐标系管理和不确定性传播；
- Agent 把 SLAM 当查询基础设施，而不是让 LLM 每次临时“调用一下定位”。

### 6.3 世界模型不能自然取代实时控制

WM 可以给规划器提供预测代价、风险或候选排序，但不能自动替代：

- 碰撞和运动学硬约束；
- 状态估计与时间同步；
- 高频轨迹跟踪、阻抗与急停；
- 经过验证的导航局部规划；
- 机器人本体动作适配。

传统方法与 WM 更像正交坐标轴：前者提供状态估计、显式约束、可检查的可行性与高频执行机制，后者提供经验性的后果预测。现实中的模型误差意味着前者也不能普遍保证成功或安全。狭窄任务上，规则可能比大 WM 更快、更稳、更易归因。

## 7. 时序、分帧与单卡资源调度

### 7.1 MVP 先采用同步 primitive 循环

~~~text
捕获 obs_N
  → 基于 obs_N 生成一个 action chunk
  → 执行该 chunk（独立安全层可随时急停）
  → MVP Verifier 在完整 chunk 边界检查
  → 更新 Task State
  → 必要时触发 Agent
  → 进入下一个 primitive
~~~

每条命令至少携带 obs_id、primitive_id、chunk_id 和 capture_time。若目标、primitive 或场景版本已经改变，由旧 obs_id 生成的动作必须丢弃。

同步模式虽然慢，却最容易保证因果归因和可复现性。系统稳定后再试：

- latest-frame-wins：推理只取最新完整帧，过期帧直接丢弃；
- 多相机 latest-complete-bundle：只组合同一时间窗内的完整相机束，记录最大时间偏差，不能把不同时间的“最新帧”伪装成同步观测；
- 短环形缓冲：只用于日志和有限时序输入，不累积无限视频；
- 双缓冲：执行当前 chunk 后半段时准备下一次观测或推理；
- chunk 内事件中断：作为 M2/A2 的增量档，每 5–10 步或在空抓、目标丢失等低成本事件发生时检查并丢弃剩余动作；
- 自适应 replanning：只有观测变化超过阈值才丢弃剩余 chunk。

### 7.2 可以分帧，不能逐帧卸载模型

摄像头 30 FPS 不代表 VLA 必须处理每一帧。可以按策略频率采样、跳帧或只保留最新帧；高频控制器继续执行缓存动作。真正不推荐的是：

> 每帧或每个 chunk 把 VLA 从 VRAM 卸载到 64 GB 系统内存，再在下一次调用时传回 GPU。

系统内存可以保存 checkpoint、CPU 权重副本、帧缓存和 trace，但 RAM→VRAM 的权重传输与 kernel 重新预热会制造长尾停顿。VLA 至少应在一批 task/seed 或整个 episode 内常驻 GPU。重型分割/感知模型若不能共存，只在阶段边界换入换出，并把换入时间计入 wall-clock。

PyTorch 的 pinned memory / non_blocking 适合图像和小张量传输，不会让整模型换入换出变成实时操作。

### 7.3 多速率职责

下面只是典型工程参考带宽，必须以本机 profile 为准：

| 回路 | 参考频率/触发 | 责任 |
|---|---|---|
| 运动控制、硬安全、力/速度限制 | 100–1000 Hz | reference 跟踪、稳定执行和紧急中断 |
| 持续感知 / SLAM / 局部规划 | 传感器驱动；局部规划常见约 10–50 Hz | 更新 belief、可行路径和 reference |
| 低成本 Verifier | 先复现原 stop cadence；M2/A2 再比较 chunk 边界与关键事件（参考 5–30 Hz） | 发现空抓和停滞；安全事件由公共安全层上报 |
| VLA | 每个 action chunk | 局部接触动作 |
| Agent | 完成、失败、超时、目标变化 | 子目标、工具与恢复 |

固定桌面机械臂不一定需要 WBC；关节控制、OSC 或阻抗控制往往更贴切。任何简单 clamp 都只能减少明显越界，不能宣称“保证接触安全”。

### 7.4 当前硬件边界

当前机器为 RTX 5070 Ti 16 GB、Core Ultra 7 265KF、64 GB RAM，无私有机器人数据。由此得到的实际边界是：

| 资源 | 推荐驻留内容 |
|---|---|
| GPU | 一个冻结 VLA + 必要仿真渲染；先做峰值显存冒烟测试 |
| CPU | 规则 Verifier、解析控制、任务状态、日志和轻量学习器 |
| RAM | 数据集、checkpoint 缓存、帧环形缓冲、trace |
| API 或 CPU 小模型 | 低频 Agent planner；必须记录网络/推理延迟 |

[openpi 官方说明](https://github.com/Physical-Intelligence/openpi/blob/main/README.md)给出的单卡估计是推理超过 8 GB、LoRA 微调超过 22.5 GB、全量微调超过 70 GB，因此 16 GB 上应把 π0.5 定位为冻结推理，而不是承诺 LoRA。是否能与仿真、分割模型同时常驻仍需实测。

openpi 官方目前说明其测试环境为 Ubuntu 22.04，并不支持其他操作系统。当前工作区运行在 Windows，因此 Phase 0 还必须验证 WSL2/Linux GPU 环境、驱动和仿真渲染链路；不能把“显存够”直接等同于“本机环境可运行”。

若使用 openpi 的 JAX 路径，还要按 [JAX GPU memory allocation](https://docs.jax.dev/en/latest/gpu_memory_allocation.html) 检查 XLA 预分配比例、warm-up 后峰值与内存碎片。关闭预分配或降低 fraction 不一定更快，只能通过本机 profile 决定。

[LeRobot 硬件指南](https://huggingface.co/docs/lerobot/main/hardware_guide)给出 SmolVLA 训练的量级估计约为 10–16 GB（batch size 8，具体受分辨率和配置影响）；当前仓库已有约 0.91 GB 的 SmolVLA base 权重，配置为 3 路 256×256 图像、6 维动作和 chunk size 50。它只能证明本地有接口开发资产，不是即插即用的 LIBERO policy。闭环实验仍需匹配 LIBERO、本体与动作 schema 的任务 checkpoint，或用公开任务数据完成适配；换用 SmolVLA 得到的是“小模型 Harness 迁移实验”，不能称 π0.5 Harness 的忠实复现。

因此 MVP 暂不包含：

- 新 VLA 预训练或 π0.5 全量/LoRA 训练；
- 本地第二个大 VLM；
- 完整生成式 WM；
- 完整语义 SLAM；
- 在线 RL；
- 每步多候选 chunk 采样；
- VLA 接触动作上的逐步 MPC 改写。

### 7.5 两种运行模式必须分开报告

1. **功能模式**：仿真可暂停等待 Agent/VLA，验证逻辑正确性；
2. **延迟感知模式**：世界持续运行，旧动作会过期，报告真实 wall-clock、deadline miss 和 stale-action drop。

若只报告第一种，结论只能是功能复现，不能称实时具身 Agent。

## 8. 可证伪的实验设计

### 8.1 Phase 0：先测可运行性

在写复杂 Agent 前完成：

1. checkpoint 加载、预热和首帧延迟；
2. 单次 VLA 推理 p50/p95；
3. 一个 chunk 的物理/仿真执行时间；
4. VLA + 仿真渲染峰值显存；
5. 连续长 episode 是否显存增长或泄漏；
6. Agent/API、Verifier 和模型换入的独立 wall-clock；
7. 世界暂停与持续运行两种模式的差异。

若 π0.5 与环境无法在 16 GB 稳定共存，优先顺序是：关闭非必要重型感知、降低渲染负担并检查 XLA 预分配 → 若存在匹配任务/动作 schema 的小 checkpoint，则用它完成 Harness 系统归因 → 只在关键最终实验租用更大显存。仿真与 VLA 分进程只能改善隔离，不会降低总显存，额外 CUDA context 甚至可能增加占用；它不是 OOM 解决方案。未适配的 SmolVLA base 只能做接口和资源测试。

### 8.2 四组主实验与小规模次级消融

主结果先围绕“忠实复现 + 一个明确改进”收缩：

| 编号 | 系统 | 目的 |
|---|---|---|
| M0 | Frozen VLA 直接执行 | 局部策略基线 |
| M1 | Faithful RPent/Harness：固定 commit，原解析原语、短 burst vla_act、原 stop predicate、Task Specific + Global Memory | 复现论文基线 |
| M2 | M1 + 超出原 stop 的确定性 typed execution Verifier | 检验标准错误类型、低成本信号或更高检查频率的增量 |
| M3 | M2 + typed competence memory | 检验统计化技能工作域能否超越原文本 Global Memory |

在 16 GB 单卡上，M1 首先追求 **protocol-faithful**：固定 RPent commit，并忠实保留 tool、stop、memory、budget 和 Agent 语义，同时把所有方法的感知固定为 P0。只有 checkpoint、感知栈、任务资产和 planner 条件也与论文一致时，才称 full-stack reproduction 并比较论文绝对数字；否则只比较本地 paired baseline。默认 RPent full extra 还包含 π0.5、仿真和重型分割服务，不能假定它们能在当前单卡同时常驻。

M2 开始前必须提交一张 code-audit 表，固定原 stop predicate 的输入、检查频率、触发时机、是否丢弃剩余 chunk、返回码和 benchmark oracle 依赖。新增机制随后只改变一个维度：

1. 先在**相同信号和相同 cadence**下比较原 stop 与 typed result；
2. 再将 typed 检查移到 chunk 内每 $k$ 步或低成本事件；
3. 明确 abort 是只终止当前 chunk、返回 planner，还是终止整个 primitive；
4. 始终保留所有方法共用的独立高频安全层。

在少量代表任务上做次级归因，不必把所有组合跑满：

| 消融 | 对照 | 公平性要求 |
|---|---|---|
| A0 Planner | 固定 FSM vs. LLM planner | 同感知、工具、stop、恢复、预算；声明 FSM 是否按任务手写、是否看过 seed 0 |
| A1 Memory | 无检索 → Task trace → Task + 原文本 Global Memory → + typed competence | 使用同一 bootstrap trace、失败样本、探索预算和检索 token 预算 |
| A2 Supervision | 原 stop → 同 cadence typed verifier → chunk 内每 $k$ 步/event | 检测策略与恢复策略分开；先在同一离线 trace 上测检测，再固定恢复策略跑闭环 |
| A3 Learned verifier | rule → learned replacement；可选 rule+learned ensemble 另列 | 输入模态、阈值选择集和测试集一致，replacement 与 ensemble 不混写 |

所有主实验与消融共享同一 checkpoint、动作适配、感知等级、工具 schema、success predicate、速度/关节/工作空间限制、高频安全层、重试/时间预算和仿真暂停策略。Agent 还要固定模型供应方与版本、temperature、系统 prompt、token/retry budget；使用多个 planner seeds，并记录 invalid tool-call、API token、费用和重试数。

新颖性不能只写成“把 VLA 当 tool”。更有价值的候选增量是：

- 相对原 stop predicate 明确定义的 typed failure 与 chunk 内中断；
- 不复用绝对坐标、且超越原文本 Global Memory 的 competence statistics；
- 面向单卡的模型常驻、丢帧与事件调度；
- 对 Agent 收益、恢复收益、bootstrap 成本和延迟代价做成对归因。

### 8.3 任务与数据协议

建议先在标准 LIBERO 做 sanity check，再把鲁棒性主结果放在 LIBERO-Pro 的对象交换、指令重定向、位置交换或等价自建扰动上。标准套件可能接近饱和，不适合单独证明 Harness 必要性；LIBERO-Pro 主要是 distribution-shift benchmark，也不能单独证明长程。

若要验证 horizon scaling，应在运行前按专家最短任务结构或 benchmark 定义预注册难度桶，例如 required subgoals、required contact phases 和 nominal episode duration。不要把方法实际调用的 primitive 数作为主要自变量，因为恢复较差的方法本来就会调用更多 primitive，这是 post-treatment 变量。

按资源逐步扩大：

- 开发阶段：4 个代表任务 × 3 个 paired seeds，快速排错；
- 最终阶段：优先 8–10 个任务 × 10 个 held-out seeds；若预算不足，保留 paired design 并报告准确分母和宽置信区间；
- 每个方法使用相同初态、随机种子和扰动；
- bootstrap seed 与评测 seed 严格分离；
- P0 因果主实验固定相同 oracle 感知；P1 只做小规模非特权输入复核；
- benchmark success predicate 默认只给 evaluator；在线暴露时单列 oracle-monitor；
- 对 memory、Agent、Verifier 分别消融，不能只看端到端成功率。

每种 memory 条件都要报告 bootstrap 所消耗的 resets、环境步数、VLA chunks、Agent 调用、wall-clock、API tokens 和费用。比较记忆表示时，应让对照获得同一批 seed 0 trace/失败样本；可用等 token 的 raw audit 对照结构化相对 trace，避免把“多了训练信息”误归因为“记忆结构更好”。

Learned Verifier 的主要监督来源是本任务自生成仿真 trace；公开数据只作为可选预训练来源，不能假设其中已有匹配 failure labels。用预抓偏移、相机偏移、遮挡、物体交换、chunk 截断、摩擦变化、延迟和丢帧构造失败，并按 task / episode / seed 划分训练、验证和测试，禁止随机拆分相邻帧。第一版依次尝试规则、Logistic Regression/LightGBM、两层 MLP；只有低维状态不够时才加入 MobileNet crop。

## 7. 时序、分帧与单卡资源调度

### 7.1 MVP 先采用同步 primitive 循环

~~~text
捕获 obs_N
  → 基于 obs_N 生成一个 action chunk
  → 执行该 chunk（独立安全层可随时急停）
  → MVP Verifier 在完整 chunk 边界检查
  → 更新 Task State
  → 必要时触发 Agent
  → 进入下一个 primitive
~~~

每条命令至少携带 obs_id、primitive_id、chunk_id 和 capture_time。若目标、primitive 或场景版本已经改变，由旧 obs_id 生成的动作必须丢弃。

同步模式虽然慢，却最容易保证因果归因和可复现性。系统稳定后再试：

- latest-frame-wins：推理只取最新完整帧，过期帧直接丢弃；
- 多相机 latest-complete-bundle：只组合同一时间窗内的完整相机束，记录最大时间偏差，不能把不同时间的“最新帧”伪装成同步观测；
- 短环形缓冲：只用于日志和有限时序输入，不累积无限视频；
- 双缓冲：执行当前 chunk 后半段时准备下一次观测或推理；
- chunk 内事件中断：作为 M2/A2 的增量档，每 5–10 步或在空抓、目标丢失等低成本事件发生时检查并丢弃剩余动作；
- 自适应 replanning：只有观测变化超过阈值才丢弃剩余 chunk。

### 7.2 可以分帧，不能逐帧卸载模型

摄像头 30 FPS 不代表 VLA 必须处理每一帧。可以按策略频率采样、跳帧或只保留最新帧；高频控制器继续执行缓存动作。真正不推荐的是：

> 每帧或每个 chunk 把 VLA 从 VRAM 卸载到 64 GB 系统内存，再在下一次调用时传回 GPU。

系统内存可以保存 checkpoint、CPU 权重副本、帧缓存和 trace，但 RAM→VRAM 的权重传输与 kernel 重新预热会制造长尾停顿。VLA 至少应在一批 task/seed 或整个 episode 内常驻 GPU。重型分割/感知模型若不能共存，只在阶段边界换入换出，并把换入时间计入 wall-clock。

PyTorch 的 pinned memory / non_blocking 适合图像和小张量传输，不会让整模型换入换出变成实时操作。

### 7.3 多速率职责

下面只是典型工程参考带宽，必须以本机 profile 为准：

| 回路 | 参考频率/触发 | 责任 |
|---|---|---|
| 运动控制、硬安全、力/速度限制 | 100–1000 Hz | reference 跟踪、稳定执行和紧急中断 |
| 持续感知 / SLAM / 局部规划 | 传感器驱动；局部规划常见约 10–50 Hz | 更新 belief、可行路径和 reference |
| 低成本 Verifier | 先复现原 stop cadence；M2/A2 再比较 chunk 边界与关键事件（参考 5–30 Hz） | 发现空抓和停滞；安全事件由公共安全层上报 |
| VLA | 每个 action chunk | 局部接触动作 |
| Agent | 完成、失败、超时、目标变化 | 子目标、工具与恢复 |

固定桌面机械臂不一定需要 WBC；关节控制、OSC 或阻抗控制往往更贴切。任何简单 clamp 都只能减少明显越界，不能宣称“保证接触安全”。

### 7.4 当前硬件边界

当前机器为 RTX 5070 Ti 16 GB、Core Ultra 7 265KF、64 GB RAM，无私有机器人数据。由此得到的实际边界是：

| 资源 | 推荐驻留内容 |
|---|---|
| GPU | 一个冻结 VLA + 必要仿真渲染；先做峰值显存冒烟测试 |
| CPU | 规则 Verifier、解析控制、任务状态、日志和轻量学习器 |
| RAM | 数据集、checkpoint 缓存、帧环形缓冲、trace |
| API 或 CPU 小模型 | 低频 Agent planner；必须记录网络/推理延迟 |

[openpi 官方说明](https://github.com/Physical-Intelligence/openpi/blob/main/README.md)给出的单卡估计是推理超过 8 GB、LoRA 微调超过 22.5 GB、全量微调超过 70 GB，因此 16 GB 上应把 π0.5 定位为冻结推理，而不是承诺 LoRA。是否能与仿真、分割模型同时常驻仍需实测。

openpi 官方目前说明其测试环境为 Ubuntu 22.04，并不支持其他操作系统。当前工作区运行在 Windows，因此 Phase 0 还必须验证 WSL2/Linux GPU 环境、驱动和仿真渲染链路；不能把“显存够”直接等同于“本机环境可运行”。

若使用 openpi 的 JAX 路径，还要按 [JAX GPU memory allocation](https://docs.jax.dev/en/latest/gpu_memory_allocation.html) 检查 XLA 预分配比例、warm-up 后峰值与内存碎片。关闭预分配或降低 fraction 不一定更快，只能通过本机 profile 决定。

[LeRobot 硬件指南](https://huggingface.co/docs/lerobot/main/hardware_guide)给出 SmolVLA 训练的量级估计约为 10–16 GB（batch size 8，具体受分辨率和配置影响）；当前仓库已有约 0.91 GB 的 SmolVLA base 权重，配置为 3 路 256×256 图像、6 维动作和 chunk size 50。它只能证明本地有接口开发资产，不是即插即用的 LIBERO policy。闭环实验仍需匹配 LIBERO、本体与动作 schema 的任务 checkpoint，或用公开任务数据完成适配；换用 SmolVLA 得到的是“小模型 Harness 迁移实验”，不能称 π0.5 Harness 的忠实复现。

因此 MVP 暂不包含：

- 新 VLA 预训练或 π0.5 全量/LoRA 训练；
- 本地第二个大 VLM；
- 完整生成式 WM；
- 完整语义 SLAM；
- 在线 RL；
- 每步多候选 chunk 采样；
- VLA 接触动作上的逐步 MPC 改写。

### 7.5 两种运行模式必须分开报告

1. **功能模式**：仿真可暂停等待 Agent/VLA，验证逻辑正确性；
2. **延迟感知模式**：世界持续运行，旧动作会过期，报告真实 wall-clock、deadline miss 和 stale-action drop。

若只报告第一种，结论只能是功能复现，不能称实时具身 Agent。

## 8. 可证伪的实验设计

### 8.1 Phase 0：先测可运行性

在写复杂 Agent 前完成：

1. checkpoint 加载、预热和首帧延迟；
2. 单次 VLA 推理 p50/p95；
3. 一个 chunk 的物理/仿真执行时间；
4. VLA + 仿真渲染峰值显存；
5. 连续长 episode 是否显存增长或泄漏；
6. Agent/API、Verifier 和模型换入的独立 wall-clock；
7. 世界暂停与持续运行两种模式的差异。

若 π0.5 与环境无法在 16 GB 稳定共存，优先顺序是：关闭非必要重型感知、降低渲染负担并检查 XLA 预分配 → 若存在匹配任务/动作 schema 的小 checkpoint，则用它完成 Harness 系统归因 → 只在关键最终实验租用更大显存。仿真与 VLA 分进程只能改善隔离，不会降低总显存，额外 CUDA context 甚至可能增加占用；它不是 OOM 解决方案。未适配的 SmolVLA base 只能做接口和资源测试。

### 8.2 四组主实验与小规模次级消融

主结果先围绕“忠实复现 + 一个明确改进”收缩：

| 编号 | 系统 | 目的 |
|---|---|---|
| M0 | Frozen VLA 直接执行 | 局部策略基线 |
| M1 | Faithful RPent/Harness：固定 commit，原解析原语、短 burst vla_act、原 stop predicate、Task Specific + Global Memory | 复现论文基线 |
| M2 | M1 + 超出原 stop 的确定性 typed execution Verifier | 检验标准错误类型、低成本信号或更高检查频率的增量 |
| M3 | M2 + typed competence memory | 检验统计化技能工作域能否超越原文本 Global Memory |

在 16 GB 单卡上，M1 首先追求 **protocol-faithful**：固定 RPent commit，并忠实保留 tool、stop、memory、budget 和 Agent 语义，同时把所有方法的感知固定为 P0。只有 checkpoint、感知栈、任务资产和 planner 条件也与论文一致时，才称 full-stack reproduction 并比较论文绝对数字；否则只比较本地 paired baseline。默认 RPent full extra 还包含 π0.5、仿真和重型分割服务，不能假定它们能在当前单卡同时常驻。

M2 开始前必须提交一张 code-audit 表，固定原 stop predicate 的输入、检查频率、触发时机、是否丢弃剩余 chunk、返回码和 benchmark oracle 依赖。新增机制随后只改变一个维度：

1. 先在**相同信号和相同 cadence**下比较原 stop 与 typed result；
2. 再将 typed 检查移到 chunk 内每 $k$ 步或低成本事件；
3. 明确 abort 是只终止当前 chunk、返回 planner，还是终止整个 primitive；
4. 始终保留所有方法共用的独立高频安全层。

在少量代表任务上做次级归因，不必把所有组合跑满：

| 消融 | 对照 | 公平性要求 |
|---|---|---|
| A0 Planner | 固定 FSM vs. LLM planner | 同感知、工具、stop、恢复、预算；声明 FSM 是否按任务手写、是否看过 seed 0 |
| A1 Memory | 无检索 → Task trace → Task + 原文本 Global Memory → + typed competence | 使用同一 bootstrap trace、失败样本、探索预算和检索 token 预算 |
| A2 Supervision | 原 stop → 同 cadence typed verifier → chunk 内每 $k$ 步/event | 检测策略与恢复策略分开；先在同一离线 trace 上测检测，再固定恢复策略跑闭环 |
| A3 Learned verifier | rule → learned replacement；可选 rule+learned ensemble 另列 | 输入模态、阈值选择集和测试集一致，replacement 与 ensemble 不混写 |

所有主实验与消融共享同一 checkpoint、动作适配、感知等级、工具 schema、success predicate、速度/关节/工作空间限制、高频安全层、重试/时间预算和仿真暂停策略。Agent 还要固定模型供应方与版本、temperature、系统 prompt、token/retry budget；使用多个 planner seeds，并记录 invalid tool-call、API token、费用和重试数。

新颖性不能只写成“把 VLA 当 tool”。更有价值的候选增量是：

- 相对原 stop predicate 明确定义的 typed failure 与 chunk 内中断；
- 不复用绝对坐标、且超越原文本 Global Memory 的 competence statistics；
- 面向单卡的模型常驻、丢帧与事件调度；
- 对 Agent 收益、恢复收益、bootstrap 成本和延迟代价做成对归因。

### 8.3 任务与数据协议

建议先在标准 LIBERO 做 sanity check，再把鲁棒性主结果放在 LIBERO-Pro 的对象交换、指令重定向、位置交换或等价自建扰动上。标准套件可能接近饱和，不适合单独证明 Harness 必要性；LIBERO-Pro 主要是 distribution-shift benchmark，也不能单独证明长程。

若要验证 horizon scaling，应在运行前按专家最短任务结构或 benchmark 定义预注册难度桶，例如 required subgoals、required contact phases 和 nominal episode duration。不要把方法实际调用的 primitive 数作为主要自变量，因为恢复较差的方法本来就会调用更多 primitive，这是 post-treatment 变量。

按资源逐步扩大：

- 开发阶段：4 个代表任务 × 3 个 paired seeds，快速排错；
- 最终阶段：优先 8–10 个任务 × 10 个 held-out seeds；若预算不足，保留 paired design 并报告准确分母和宽置信区间；
- 每个方法使用相同初态、随机种子和扰动；
- bootstrap seed 与评测 seed 严格分离；
- P0 因果主实验固定相同 oracle 感知；P1 只做小规模非特权输入复核；
- benchmark success predicate 默认只给 evaluator；在线暴露时单列 oracle-monitor；
- 对 memory、Agent、Verifier 分别消融，不能只看端到端成功率。

每种 memory 条件都要报告 bootstrap 所消耗的 resets、环境步数、VLA chunks、Agent 调用、wall-clock、API tokens 和费用。比较记忆表示时，应让对照获得同一批 seed 0 trace/失败样本；可用等 token 的 raw audit 对照结构化相对 trace，避免把“多了训练信息”误归因为“记忆结构更好”。

Learned Verifier 的主要监督来源是本任务自生成仿真 trace；公开数据只作为可选预训练来源，不能假设其中已有匹配 failure labels。用预抓偏移、相机偏移、遮挡、物体交换、chunk 截断、摩擦变化、延迟和丢帧构造失败，并按 task / episode / seed 划分训练、验证和测试，禁止随机拆分相邻帧。第一版依次尝试规则、Logistic Regression/LightGBM、两层 MLP；只有低维状态不够时才加入 MobileNet crop。

### 8.4 指标

**任务效果**

- Episode Success Rate；
- Success Rate vs. 预注册的 required subgoals / contact phases / nominal duration；
- 实际 primitive 与 VLA 调用数仅作为效率/失败结果，不作为 horizon 的主分组变量；
- 子目标完成率与目标重绑定准确率；
- 放置位置/姿态误差。

**失败发现与恢复**

$$
\text{Recovery Rate}=
\frac{\text{检测到失败后最终成功的 episode}}
{\text{存在可恢复失败的 episode}}
$$

“可恢复失败”必须在实验前按注入扰动与 oracle recovery path 操作化定义，不能看到某方法后来恢复了才事后计入分母。

- empty grasp / stalled 检测 precision、recall、F1；
- 失败发生到中断的延迟；
- 失败后浪费的 action steps / chunks；
- 相同失败重复率；
- 安全层介入和碰撞次数。

**系统代价**

- Agent、VLA、Verifier 延迟 p50/p95；
- Agent/VLA 调用次数；
- invalid tool-call、planner retries、API tokens 与费用；
- episode wall-clock 与成功任务 wall-clock；
