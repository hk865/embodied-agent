# 具身 Agent 基础实验流程

## 1. 实验目标

本流程服务于一个可复现的核心问题：

> 固定低层 VLA 与环境后，Agent/Harness 的规划、Verifier、恢复和记忆分别改变了什么？

流程刻意把“系统能跑通”和“研究结论成立”分开。前者允许 oracle 状态和少量任务排错；后者必须使用冻结协议、留出 seed 和可比较预算。

## 2. 总流程

```mermaid
flowchart LR
    Q["研究问题与最小效应"] --> P["预注册实验组和指标"]
    P --> E["冻结环境 / checkpoint / 接口"]
    E --> S0["Phase 0 资源与动作冒烟"]
    S0 --> B["B0/B1/B2 基线"]
    B --> A["B3/B4 单变量增量"]
    A --> R["配对 seed 正式运行"]
    R --> T["Trace 审计与统计"]
    T --> C["结论、边界与失败条件"]
```

## 3. Phase 0：资源与接口可行性

这一阶段不比较方法，只回答系统能否稳定运行。

### 3.1 固定版本

记录：

- 操作系统、WSL/Linux、GPU 驱动与 CUDA；
- 仿真器、benchmark、VLA 后端和依赖 commit；
- checkpoint 名称、来源、哈希、精度与量化；
- 相机名称、分辨率、顺序和时间同步窗口；
- 动作维度、坐标系、绝对/增量表示、归一化统计；
- action chunk 长度、控制频率和剩余动作丢弃规则。

### 3.2 最小冒烟测试

1. 环境 reset 后观测维度正确；
2. checkpoint 加载和 warm-up 成功；
3. 用固定观测重复推理，输出无 NaN / 越界；
4. 动作反归一化和机器人接口一致；
5. 在一个匹配任务上完成至少若干连续 chunk；
6. 终止谓词、超时和异常能返回标准结果；
7. 长回合无持续显存增长或句柄泄漏。

### 3.3 必测资源数据

| 指标 | 测量方法 | 用途 |
|---|---|---|
| 首帧延迟 | 冷启动到首个动作 | 区分启动成本 |
| VLA p50 / p95 | warm-up 后多次推理 | 判断闭环频率 |
| Agent p50 / p95 | 固定 prompt 与工具数 | 判断重规划代价 |
| 峰值显存 | 加载、warm-up、长回合分别记录 | 判断 16 GB 可行性 |
| 一个 chunk 执行时间 | 仿真步与墙钟同时记录 | 计算监督窗口 |
| 过期动作 | `action.obs_id != latest_obs_id` | 判断异步必要性 |

若 VLA、仿真和感知无法同时稳定运行，先减少重型感知和渲染负担，再换匹配任务的小型 checkpoint；不要用未适配的基础模型报告闭环策略结论。

## 4. Phase 1：任务与扰动冻结

### 4.1 任务清单

为每个任务记录：

```yaml
task_id: libero_goal_01
instruction: "..."
benchmark_version: "..."
horizon:
  subgoals: 3
  primitives: 5
  contact_phases: 2
max_env_steps: 600
max_vla_chunks: 12
max_retries: 2
success_predicate: "..."
recoverable_failures:
  - EMPTY_GRASP
  - TARGET_LOST
```

“长程”至少按子目标数、原语数、接触阶段数和物理时长描述，不能只写 prompt 长度或视频时长。

### 4.2 Seed 划分

建议分为：

- `dev`：少量任务 × 少量 seed，仅排错；
- `bootstrap`：构造 Task / Global / Competence Memory；
- `eval`：正式留出 seed，冻结 prompt、规则和持久记忆；
- `stress`：遮挡、对象交换、预对位偏移、摩擦变化、延迟和丢帧。

相邻视频帧不能跨 train / validation / test；同一 episode 的切片必须属于同一划分。

### 4.3 感知等级

| 等级 | 数据 | 用途 |
|---|---|---|
| P0 Oracle | 仿真对象位姿、接触等特权状态 | 因果主实验和上界；明确标注不可部署 |
| P1 Minimal | RGB-D、轻量检测/分割、跟踪、proprioception | 部署性复核 |
| P2 Heavy | 大型 VLM/分割服务 | 仅在 P1 明确不足时加入 |

benchmark 的成功谓词默认只给 evaluator 与 episode termination，不能无声明地作为 Agent 观测。

## 5. Phase 2：先跑基线

按 [Baseline 与评测矩阵](03-Baseline与评测矩阵.md) 依次完成：

1. B0 Frozen VLA；
2. B1 Fixed FSM；
3. B2 固定 commit 的 Harness 协议复现。

只有 B0–B2 在相同 seed 上稳定后，才开发 B3 / B4。否则增量组的提升可能只是修复了基线 bug。

### 5.1 基线验收

- 同一配置重复运行结果在合理方差内；
- reset、观测、动作和成功谓词已人工审计；
- 失败类型可以从 trace 重建；
- 每个组别使用相同总环境步数、chunk、重试和墙钟预算；
- 若与论文配置不完全一致，只报告本地成对差值。

## 6. Phase 3：单变量增量

建议顺序：

1. B2 → B3：先保持原检查周期，只改变结果语义；
2. V1 → V2：再增加 chunk 内事件检查；
3. B3 → B4：用等信息量结构化记忆替换文本记忆；
4. A0：同一 Harness 下比较 FSM 与 LLM；
5. 仅当规则达到稳定上限后做 learned verifier。

每次变更填写 [实验预注册模板](../templates/实验预注册模板.md)，明确唯一自变量。

## 7. 运行时 Trace 契约

每个事件一条记录，至少包含：

```json
{
  "run_id": "20260818_B3_task01_seed07",
  "task_id": "task01",
  "seed": 7,
  "method": "B3_typed_verifier",
  "mode": "latency_aware",
  "event_time": 1787011200.123,
  "event_type": "PRIMITIVE_RESULT",
  "obs_id": "obs_0042",
  "primitive_id": "pick_v2_0007",
  "chunk_id": "chunk_0019",
  "status": "EMPTY_GRASP",
  "evidence": {
    "gripper_width": 0.011,
    "object_track_confidence": 0.84
  },
  "agent_latency_ms": 0,
  "vla_latency_ms": 143,
  "env_step": 284,
  "recoverable": true
}
```

推荐事件类型：

- `EPISODE_START / END`；
- `OBS_CAPTURED`；
- `AGENT_DECISION`；
- `PRIMITIVE_START / RESULT`；
- `VLA_INFERENCE / CHUNK_EXECUTED`；
- `VERIFIER_EVENT`；
- `MEMORY_READ / WRITE`；
- `SAFETY_INTERRUPT`；
- `ACTION_DROPPED_STALE`。

所有动作必须能追溯到 `obs_id`。目标、primitive 版本或环境 episode 改变后，旧动作作废。

## 8. 功能模式与延迟感知模式

### 功能模式

- 仿真允许等待 Agent / VLA；
- 用于验证规划、工具调用、校验和恢复逻辑；
- 结果只支持“执行逻辑有效”。

### 延迟感知模式

- 世界在模型推理时继续运行；
- 记录 wall-clock、过期动作、deadline miss 和真实吞吐；
- 只有该模式仍有净收益，才支持实时部署价值。

两种模式不能合并成一个成功率。

## 9. 指标计算

### 9.1 任务指标

$$
\text{SuccessRate}=\frac{N_{success}}{N_{episodes}}
$$

按任务先求平均，再对任务宏平均，避免回合数多的任务主导结果。

### 9.2 恢复率

$$
\text{RecoveryRate}=\frac{N_{recovered\ recoverable\ failures}}{N_{predefined\ recoverable\ failures}}
$$

分母由预先定义的可恢复扰动和 oracle recovery path 决定，不能按方法是否恢复成功事后筛选。

### 9.3 失败发现延迟

$$
\Delta t_{detect}=t_{verifier\ event}-t_{failure\ onset}
$$

同时报告环境步数、action chunk 数和墙钟时间三种单位。

### 9.4 记忆收益

至少同时报告：

- 留出 seed 成功率增量；
- 同类失败重复率变化；
- 检索命中与错误检索；
- bootstrap 环境步数、VLA / Agent 调用和墙钟成本。

## 10. 统计与结果表

- 方法间使用相同任务和 seed 的配对设计；
- 按任务聚类 bootstrap 95% 置信区间；
- 既报告成功率，也报告成对差值；
- 不根据中途效果提前停止或改主终点；
- 所有失败 episode 保留，不删除“异常值”；
- 将 OOM、超时和安全中断计入系统失败，并单独统计。

## 11. 每次运行的产物

建议在 `workspace/experiments/<experiment_id>/` 保存：

```text
<experiment_id>/
├── preregistration.md
├── config.yaml
├── environment.lock
├── manifest.csv              # task × seed × method
├── traces/                   # JSONL，逐事件

├── metrics_summary.csv

```

使用 [实验记录模板](../templates/实验记录模板.md) 记录单次实验，禁止只在聊天记录或 notebook 输出里保存关键配置。

## 12. 最小里程碑

| 里程碑 | 完成条件 |
|---|---|
| M0 接口 | 1 个任务连续运行，动作与终止语义正确 |
| M1 基线 | B0/B1 同 seed 可重复，资源数据齐全 |
| M2 协议 | B2 固定 commit，工具、记忆和谓词审计完成 |
| M3 校验 | V0/V1/V2 单变量比较完成 |
| M4 记忆 | M0–M3 留出 seed 比较及 bootstrap 成本完成 |
| M5 实时 | 功能与延迟感知模式分别报告 |

到 M4 已能形成一个有明确正负结论的研究项目；learned verifier、世界模型和真机扩展都应在此后按证据决定。
